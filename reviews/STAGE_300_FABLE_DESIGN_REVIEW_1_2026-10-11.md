## Blocking findings

**1. Admission atomicity is asserted, not specified (design lines 20–24, 64–68).**
"Stable lock ordering and one transaction" is not sufficient on its own. If the implementation keeps an append-only journal and computes remaining capacity as a SUM inside a READ COMMITTED transaction, two processes can both read the same remaining amount and both insert a reservation. Nothing in the design forbids that reading, and the required "concurrent/multi-process oversubscription" test (line 152) can pass by timing luck. Three sub-gaps:

- The design never names what is locked. Lock targets must be the scope keys themselves (global UTC day, campaign UTC day, session), acquired before the remaining amount is read.
- Line 23 says to persist a reservation "state", which implies a mutable row. `apps/server/migrations/AGENTS.md:9` says later domains append rather than add mutable state tables unless an ADR says otherwise. The design must choose and record the choice; "Current ADR" is in the allowed boundaries (line 138), so this is cheap.
- "Session" is undefined. The work order's "per session" is a 45-minute play session; the codebase's session identity is a login session. The design mentions "evaluation/session ceilings" (line 20) and "parent request/session budget" (line 28) without saying what key identifies a runtime session.

Resolution: specify, in §1, that admission runs in one transaction that first takes `pg_advisory_xact_lock` on each applicable scope key in sorted order (or `SELECT ... FOR UPDATE` on per-scope counter rows created idempotently with `ON CONFLICT DO NOTHING`), then reads outstanding reservations plus settled spend for those scopes, then inserts the reservation and the attempt-start row. Period assignment uses the database clock, not the application clock, so two processes with skewed clocks cannot straddle midnight differently. State the store shape: either append-only reservation/settlement event rows with state derived under the lock, or a mutable `ltw_ai_budget_attempts` row with a guarded transition (`UPDATE ... WHERE state = 'reserved'`) and an ADR 0032 amendment allowing it. Define the session key: for evaluation, the run manifest ID; for runtime, state whether the session ceiling is per campaign per server process, per DM login session, or dropped in favour of campaign-day (the work order's requirement is campaign and day; session is additive). Add to the test list a two-connection test that interleaves two admissions at the ceiling boundary and asserts exactly one admits.

**2. The input-token bound rule makes the system either unimplementable or impractical (lines 31–33).**
The design permits only two paths: a "verified offline input-token bound" or reserving the full model input limit. It then forbids "a guessed token heuristic" without saying what counts as verified. No provider in the catalog publishes a tokenizer the implementer can run offline and call verified, so the sanctioned path collapses to full-limit reservation. For Claude Opus 5.5 that is roughly 200k tokens of input at $4/M plus 4,096 output at $20/M, over $0.85 per reservation before the cache-write multiplier. Reservations are released at settlement, so sequential use survives, but any ceiling in the $20 range denies admission well before real spend approaches it, and two concurrent DM requests would deny each other. The design, as written, lets a correct implementation ship a budget gate that mostly says no.

Resolution: name the accepted bound in §1. Recommended: enforce the request-size limit already required on line 34 in UTF-8 bytes, and reserve input as `bytes + fixed framing and schema allowance` tokens, justified once per catalog entry by the property that byte-level BPE never yields more tokens than bytes. Record that justification per model in the catalog with the date and the check performed (for Anthropic, a one-time comparison against the free token-counting endpoint during catalog verification, not at runtime; for DeepSeek, the published tokenizer). The output side stays at the enforced `max_tokens`. State explicitly that this is the "verified offline bound" and that full-limit reservation is the fallback only for a model whose catalog entry lacks the justification.

**3. Refusal and no-tool-call handling is left undecided against ADR 0017 §5 (lines 79–84, 93–98).**
Baseline `anthropic-provider.ts:113–122` throws `BAD_RESPONSE` for a refusal or a prose reply without the tool call. `fallback.ts:74–93` treats any throw as provider failure and switches providers; it never repairs. ADR 0017 §5 says invalid structured output gets one repair on the same provider, and ADR 0032 §1 claims "the gateway's repair and fallback policy applies", which is only half true. The design notices this ("do not claim repair when the implementation only switches") but does not decide which behaviour is the contract. This matters for budget too: a repair is a second paid admission, a switch to local is free.

Resolution: decide in §3 and record in ADR 0032. Recommended split: a provider-signalled refusal (`stop_reason: refusal`) is a terminal non-error outcome with usage preserved, no repair, no switch, outcome recorded as a fixed code. A prose reply with no tool call is invalid structured output and gets the one repair ADR 0017 §5 owes it, on the same provider, under a separate admission. The deliberate no-proposal decline (lines 93–98) must be validated as a typed valid result so it triggers neither repair nor switch. Say so explicitly, because otherwise "avoid a paid schema-repair attempt" conflicts with ADR 0017 §5's repair rule. Keep the public response as today's `INVALID_OUTPUT` with one fixed issue string, record the decline in the trace's additive attempt metadata, and have the eval read that field rather than the baseline's substring test at `eval-cli.ts:113–116`.

**4. Trusted accounting identity has no defined channel, and the admission wrapper is not made mandatory (lines 25–26, 65–68).**
Baseline `ProviderRequest` carries no campaign or trace identity, which is why ADR 0032 §4 could not implement a campaign ceiling. Baseline `relevance.ts:146` and `intent.ts:77` allocate the trace ID after the provider call returns, so "register the parent trace/attempt identity before dispatch" cannot be satisfied without reordering. The design lists `providers.ts`, `fallback.ts` and the use-case files as allowed boundaries but does not say what changes, and it does not require that every remote provider be reachable only through the admission wrapper. `gateway.ts:47–81` happens to wrap every remote in `budgeted()`, but nothing tests that, and the eval composes its own gateway.

Resolution: state in §2 that `ProviderRequest` gains a required `accounting` field (campaign ID, pre-allocated trace ID, attempt ID, capability, kind) populated by the use case in `@ltw/ai`, never serialised into system or prompt text; that trace IDs are allocated before the first dispatch; that the only server-side path to a remote adapter is the admission wrapper, enforced by a router-level test; and that the journal has no foreign key to `ltw_ai_traces` because the trace row is inserted later and may never arrive after a crash. Orphan journal rows are legitimate spend evidence, filtered on DM reads by the journal's own campaign column.

## Non-blocking clarifications to fold into draft 2

- **Pre-dispatch proof (line 45).** Define "proof that the transport did not run" as a distinct adapter error class thrown strictly before the transport call, including the already-aborted-signal case. Any other failure is ambiguous and keeps the hold.
- **Reconciliation (lines 37–38, 49–50).** Overrun, unexpected returned model, and crash-held reservations all end in a persisted "remote admission disabled" or "held" state with no defined way out. Name the manual step (a migration-safe CLI or documented SQL under the owner's control) and require startup to report the disabled state. Also say whether an unexpected-model response's output is used: recommend discarding it as `BAD_RESPONSE`.
- **Usage components (lines 100–103).** Anthropic reports `cache_creation_input_tokens` and `cache_read_input_tokens` separately from `input_tokens`; DeepSeek reports cache hit and miss tokens. Baseline `anthropic-provider.ts:126–128` reads only two fields and would undercount billed input once caching is on. Require adapters to capture every billed component and the catalog to price each, with the cache-write multiplier included in the reservation bound.
- **Admission inside the relevance budget (lines 72–75).** The admission transaction runs inside the 2 s deadline. Require admission to observe the abort signal, and treat a slow store the same as a store failure: deny and fall back deterministically. Record the caller timeout as a non-accounting event so the later provider settlement remains the single accounting terminal.
- **Route validation (lines 83–91).** Baseline `gateway.ts:89–94` silently drops entries whose key is missing. The design's startup report covers the `remote,local` without-key case; say explicitly that the resolved route is logged as `local` and that rejection of multi-remote and three-entry routes happens at config load, so a misconfigured server does not start in a paid state it did not declare.
- **Evaluation ledger (lines 111–112).** A durable ledger shared across reruns implies the eval CLI needs PostgreSQL. Baseline `eval-cli.ts:54–60` builds a fresh in-memory ledger per model. Say the eval requires the database and refuses to run otherwise. Baseline also writes the blind key beside the blind file and overwrites results in place; the design's immutable run directory covers the second, and should say where the key lives.
- **Eval predicates (lines 117–120).** Baseline `eval-cli.ts:133` passes any `mustNotCommit` case that returns either `PROPOSED` or `INVALID_OUTPUT`, which is nearly every outcome. The design's wording covers this; add it to the explicit list of predicates to replace, alongside the hardcoded 2000 ms at line 249.

## What is sound and should stay

Microdollar integers with upward rounding; worst-case reservation before dispatch with per-attempt admission for repair and switch; conservative hold on every post-dispatch ambiguity with no automatic expiry; settlement to the admission period across midnight; idempotent settlement; removal of the generic price fallback at `budget.ts:18`; usage preserved on refusal, malformed and truncated output; separate append-only journal resolved on DM trace reads instead of mutating `ltw_ai_traces`; deterministic relevance response at the deadline with late output never applied; single explicit relevance remote consistent with ADR 0021 §5; no default $5 approval; no paid calls until the owner supplies text-provider ceilings; evidence immutability and model-identity recording in the eval. None of these weaken invariants 1, 2, 5, 6, 9, 18, 21 or 22, and the design correctly leaves context builders, legal actions and canonical mutation untouched.

With findings 1 through 4 resolved in the text, I would expect to approve draft 2 without further architectural change.
